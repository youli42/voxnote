## 一、项目意图的演进

| 轮次 | 提出的诉求 | 结论性认识 |
| --- | --- | --- |
| 1 | 想懂"录音时监控、停录即停"是怎么实现的，以及资源占用 | 不是事件监听，是**定时轮询 + 日志锚点判会话生死**；资源被 `relink` 拖累（见 D4） |
| 2 | 能否监听按键，在按下录音键时确认录音真的触发 | 可行，且**不必依赖按键**：设备自带的埋点事件流已含逐次按键与启停 |
| 3 | 录音结束后日志里的文本会不会丢 | 分四层判据；尾句问题**实测未兑现**，但发现另外两处真会丢/出错（D1、D2） |
| 4 | 能否用一个程序静态分析日志拿到全部数据，不写模块 | 可以；解析不该在手机里做；但当时新增了一个"保留期"顾虑，**该顾虑已在第 5 轮被推翻** |
| 5 | 补充：服务器连不上、日志传不上去，还会清理吗 | **不会清理**，且逐句文本所在的 `app/` 目录根本不参与上传-删除循环 |
| 6 | 真实目标：**本地处理好数据**，自研精简安卓 App 来阅读/编辑，并支撑未来的同步与自动化 | 产物必须从"给人看的 Markdown"升级为**结构化数据 + 三层分离（机器抄的 / 你写的 / 导出物）** |
| 7 | 目标扩大：该软件未来**直接替代搜狗录音 App**；可移植到其他安卓设备；允许**自定义监控按键**；可对接**自建语音转文本 API**；在更好的设备上**下载语音小模型** | 项目性质从"日志提取器"变为"**录音+转写平台**"；日志解析降级为数据入口之一；需要**平台抽象层**与分阶段接管路线 |
| 8 | 完整整理需求与现状 | 本文档 |

## 二、需求清单（按优先级分层）

### R1 必须（当前迭代就要成立）

- **R1.1 不丢内容**：任何一场录音，要么有完整文稿，要么有**显式失败状态**（绝不允许"看起来正常的空稿"）。
- **R1.2 结构化数据底座**：会话 / 逐句 / 编辑 / 标记 四类对象有稳定 ID，可重算、可合并、可重跑。
- **R1.3 编辑不被覆盖**：机器派生结果可无限重放；人工编辑是独立追加层，永不因重解析而丢失。
- **R1.4 阅读与逐句编辑可用**：在本机 720×1280 触摸屏上完成"读一场 → 改若干句 → 存盘 → 导出"闭环。
- **R1.5 历史不锁死**：数据必须能整目录拷走/重建，卸载 App、换设备、恢复出厂都不丢。
- **R1.6 真触发判定**：能回答"这次按键到底录上了没有"，并给出证据链（按键 → 引擎启动 → 音频落盘 → 识别出字）。

### R2 应当（替代搜狗的前提条件）

- **R2.1 自录能力**：`AudioRecord` 采集、分段落盘、时长/电平/VAD、断点保护、异常中断可识别。
- **R2.2 可插拔转写引擎**：统一 `partial/final` 流式接口，四种后端可共存 —— 自建云 API / 本地小模型 / 外部导入（含搜狗日志）/ 人工。
- **R2.3 引擎结果可重跑**：记录引擎名+版本+耗时+置信度+错误；换 API、换模型、联网恢复后可对同一音频重算。
- **R2.4 按键来源抽象 + 自定义映射**：捕获向导（按一次键 → 记录 → 绑定动作），按机型保存映射；不同来源（媒体键 / 焦点键 / 厂商广播 / 无障碍 / root evdev）统一抽象。
- **R2.5 可移植性**：设备差异全部收敛到平台层"能力问卷"，上层不猜机型；跨 Android 8→15 的存储、后台麦克风、通知、按键权限差异有明确降级路径。
- **R2.6 离线兜底**：无网络时本地模型可出稿（现状：这台机器断网 = 全篇无字，`errorCode 14`）。

### R3 后续（架构预留接口，不立刻实现）

- **R3.1 同步**：先文件级（整个数据目录可 rsync/Syncthing/MTP 拷），再记录级（改动序号 LWW：同一段谁的序号大听谁的）。
- **R3.2 自动化**：导出目录 + 清单文件（每场一行，含状态与路径）供 PC/手机端 watcher 消费。
- **R3.3 模型管理**：下载 / 校验 / 空间预算 / 删除；按网络、语言、电量、实测 RTF 做本地-云路由。
- **R3.4 云端字段预留**：`objectKey` / `transferDocPath` / `needReRecognize` 等厂商库中已存在的字段先占位，将来若服务恢复可直接对接。

### R4 明确不做（除非需求变更）

- 不抓取/改写搜狗的私有数据、不注入其进程（现有模块的"纯脚本、不 `system/`"边界在替代完成后即可整体作废）。
- 多端**并发**实时编辑合并（CRDT 类）——用 LWW 够用。
- 为省资源而牺牲正确性（例如用极短的去抖窗口换快出稿）。

### 3.4 清理与保留行为 **[实测]** —— 关键结论

- 上传链路：`LogRepository.kt:307 scanFile:/sdcard/sogou/log/**statistics**/…` → `:316/:324/:325 uploadStatistics` → `:345 upload file:` → `:428 #UploadPing`「**ping upload failed —上传回调失败**」**×32，全部失败**。
- **失败即不删**：同一批待传文件被跨小时重试最多 9 次，至今仍在磁盘上。
- **`app/` 目录从不出现在上传扫描路径里** → 承载正文的目录没有"上传成功后清理"这条路径。
- 偏好设置里只有 `commlog_enable=true` / `errorlog_enable=true`，**没有任何按天数 / 按大小 / 按个数的清理配置键**；18,918 行日志里**没有一条删除日志文件的事件**。
- 体积增速 **~3.3 MB/天**，其中上报重试噪声 143 KB（**5%**）。
- 无任何云端副本：`objectKey` 空、`transferDocPath` 空、`transferResultWordCnt=0`、`storage_usage="0s"`、`transfer_time_left="0s"`。
- **推论**：逐句转录文本的全球唯一副本 = 本机 `/sdcard/sogou/log/app/`，且它在可预见的将来只增不删。[推断] 剩余的清零风险只有：恢复出厂 / 清除应用数据 / 手动清理 / 未知的未来策略。

### 3.5 现状的能力账（对账基线）

```
49 次按键(rec_press) + 12 次长按 + 39 次其他键
   → 19 次 record_start（其中 3 次 nonet = 按下时无网）
      → 34 个 Builder（引擎创建，≠ 录音场次）
         → 14 行 session（今天 11 场） = 11 个 wav
            → 28 份出稿（其中 9 份是 525–534 B 空稿 + 1 份 1970 鬼稿）
               → 267 句识别行（36 final + 231 partial）全部已入 events.tsv，与日志逐行对齐
```
这五个数字的差集就是"按了没启动 / 启动了没落盘 / 落盘没出字"的清单——**新平台的对账报表应当是这条链路的自动化版本**。

## 四、已知缺陷（现有实现，全部有物证）

| ID | 缺陷 | 严重度 | 证据 | 归属 |
| --- | --- | --- | --- | --- |
| **D1** | **有内容却永远出不了稿**：`onAudioEnd` 不带 sid，只能盖给"当时的 `g_SID`"，同一次录音里较早创建的会话永远拿不到结束锚点 | 高 | `cur/1575158447.summary`、`cur/1792506705.summary` 等内容滞留；7 个孤儿 `.meta` | S0 修 |
| **D2** | **`sessionId:0` 被当合法会话** → 产出 `md/1970.01/19700101_080000_0.md`，且 `[ -n "$g_SID" ] || g_SID=$hs` 会把全局 sid 污染成 `"0"`（串台） | 中 | 12-01 基准日志里恰好 1 条 `updateSummary…,sessionId:0`；鬼稿存在 | S0 修 |
| **D3** | **把引擎重建当新录音**：34 个 Builder 对 11 场真录音 → 9 份空稿 + 目录噪声 | 中 | 空稿体积 525 B 成簇；时间戳 2 秒间隔 | S0（改认 wav/session 为主键） |
| **D4** | **`relink` 每轮遍历待挂表**，逐条起 `date`+`ls`+`head` → 实测 **~54 fork / 2 s（≈220 万次/天）**，且随空稿数线性增长 | 中 | `pending/list` = 17 条；代码 `tick → relink` 无频控 | 现有模块需修；迁 App 后自然消失 |
| **D5** | **去抖计时起点错**：`SETTLE` 从"第一条结束锚点"起算，不是"最后一条新文本" | 低（当前未兑现） | 尾句实测最大滞后 **619 ms** ≪ 窗口 6 s；`backfill` 一次读完天然免疫 | S0（改成"安静窗口"） |
| **D6** | **增量偏移按 basename 记账**，轮转改名后新名无偏移记录 → 整文件重放（重复句风险） | 中（今天未发作） | 活跃文件 `tmlog.tm` 改名即触发；现靠 `done/` 门侥幸挡住 | S0（按 inode 或内容 hash 幂等） |
| **D7** | **失败静默**：0 句 + 0 错 + 无摘要 → 直接 `touch done`；`events.tsv` 无轮转 | 中 | 9 份空稿外观正常 | R1.1 |
| **D8** | **跨文件顺序依赖秒级 mtime**，同秒并列时次序未定义 | 低 | 现有 `ls -l` 中确有两组同秒文件 | S0 |

## 五、已被推翻的判断（防止按旧结论行动）

| 曾经的说法 | 现状 |
| --- | --- |
| 「录音结束后**尾句正在被丢**」 | **错**。实测滞后 ≤619 ms，当前 6 s 窗口够用；**但机制仍脆弱**（D5），值得顺手修 |
| 「日志只保留 2 天，是纯 PC / 无模块方案的**命门**」 | **错**。2 天是**这台设备的使用年龄**（到手不足一天），不是保留策略 |

| 「模块资源占用 ≈8.6 万 fork/天、CPU <1%」 | **低估 25–27 倍**。实测 ~220 万 fork/天（D4） |
| 「数据真相放纯文件更稳」 | 目标升级为替代级 App 后改为：**SQLite 为真相 + 文件为可重生交换格式 + 双向可重建** |

## 七、目标架构（替代级）

```
┌ UI      列表 / 阅读 / 逐句编辑 / 打点 / 搜索 / 设置（按键映射·引擎选择·模型管理·能力问卷）
├ 集成    同步(文件级 → 记录级 LWW) · 导出(md/jsonl/txt) · watcher · 备份
├ 数据 ★  sessions · segments · edits · marks · engine_runs · jobs · watermarks · raw_archive
├ 转录    Engine 统一流（partial/final）：CloudAsr(自建API) | LocalAsr(模型) | Importer(搜狗日志) | Manual
├ 采集    AudioRecord · 前台服务 · VAD/电平 · 分段落盘 · 按键触发 · 中断恢复
└ 平台    Capabilities · KeySource · StorageLayout · AudioRoute · RootAccess
```

**数据三原则**（R1.3 的具体化）：派生层可无限重放；人工层只追加、永不重生成；导出层随时可删可重建。`segId` 必须确定性（由 会话 + 起止 + 原文哈希 派生），否则重放会冲掉编辑。

**跨 Android 版本的硬约束**（移植必踩，需平台层吸收）：

## 十、需要你拍板（未定即开工的只有 S0，其余都受影响）

1. **共存还是替代**：要不要动搜狗 App（决定 S2/S3 是否需要，以及是否接受 root 依赖）。
2. **自建 ASR API 的形态**（M5）：REST 短音频还是 WebSocket 流式？决定引擎接口以流式还是文件为中心。
3. **本地模型偏好**（M4/R3.3）：sherpa-onnx 流式中文（小/快/中文好）· whisper（多语种/离线全能/更慢）· 还是按语言路由两个都留。
4. **minSdk / targetSdk**：建议 minSdk 24（覆盖本机 8.1）+ targetSdk 33/34，功能按能力探测降级。
5. **公共数据目录的落法**：SAF 授权的公共文件夹（可见、可同步）还是 MediaStore（更规范、可被系统识别为音频）——影响 R1.5 与同步形态。
6. **同步是否需要多端并发编辑**：只需"改动序号 LWW"（简单可靠）还是要考虑真正的冲突合并。
