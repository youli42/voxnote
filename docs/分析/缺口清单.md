# 全局缺口清单（Gap Analysis）

> 2026-10-26。对照 [结构设计](../设计/架构设计.md)、[目标流程](../流程/目标流程.md)、[现流程](../流程/现有流程.md)
> 和现有代码做的系统扫描：列出**还没想到 / 想到了但没定细节**的地方。
>
> 每条按"细节 → 风险 → 建议"写，末尾标优先级：
> **P0** = 动工前必须定；**P1** = 第一版必须做；**P2** = 可以后置。

## 0. 结论：还有 5 个设计决定没定

这五件事不定，后面会返工：

1. **转写质量策略**：低置信/幻觉/热词/混语种怎么处理（直接存？标记？重转？）；
2. **人工修订的跨尝试重挂接**：算法和阈值、拆句/并句/整段删除怎么跟随；
3. **离线恢复**：设备离线很久、changes 过期后怎么全量兜底；
4. **存储生命周期**：音频/尝试/备份保留多久、何时删、怎么彻底删；
5. **安全边界**：引擎地址与手机直连的信任模型（SSRF、令牌、明文局域网、备份加密）。

## 1. 时间与时间轴（最容易被低估）

- **设备时钟偏差**：`recorded_at` 来自手机，多设备排序/`changes` 去重若混用时间会乱。
  建议：展示和排序用设备时间；**协议只认服务器 `rev`**，时间不参与同步判定。
- **时区与夏令时**：库里一律存 UTC 毫秒；展示按本地时区；导出带时区说明。
- **时钟回拨 / 未来时间**：现有服务端有钳制，客户端也要；排序用 `(recorded_at, id)` 稳定。
- **同一秒多条录音**：UUID 解决主键；但"时间线"要按 `recorded_at` + 稳定次序，不能只按时间。
- **音频时间轴基准**：句时间相对音频文件开头；若将来支持暂停/分段录音，需要
  `audio_start_offset` 或在合并时重算，否则播放跳句会偏。
- **时长来源冲突**：设备上报值 vs 引擎 `duration` vs 播放器实际；建议以文件/引擎为准，
  设备值只做占位；界面显示"约"。
- **时间戳精度**：库里存毫秒整数；导出 md 不再损失到 10ms 级；SRT 用毫秒。
- **服务端时间 vs 引擎时间**：尝试的 `created_at` 用服务器时间（决定质量排序的同档先后），
  引擎耗时另存；不要用引擎机器时钟。

## 2. Android 录音生命周期（当前最大的硬缺口）

现在 App **没有 Service/前台服务/通知权限**，锁屏或切后台能不能录，取决于系统与机型。

- **后台录音**：Android 10+ 禁止后台采集麦克风，必须前台服务 + 常驻通知；13+ 要通知权限；
  14+ 前台服务要声明 `microphone` 类型。**不做，锁屏/切应用随时可能断**（P1 必须）。
- **来电 / 音频焦点 / 蓝牙切换**：录音中被电话、语音助手、耳机切换打断；
  需要监听音频焦点丢失，标记"录音中断"并保留已录部分，而不是静默丢失。
- **进程被杀 / 断电 / 卡死**：临时文件与"正在录音"标记要能恢复；
  启动时检测未完成录音，提示"上次录音中断，已保留 N 秒"。
- **存储满 / 权限被回收**：录音前预检剩余空间；SAF 授权失效、MediaStore 写入失败要有
  明确降级与提示（现有写失败降级到私有目录，但没有前置检查）。
- **锁屏控制 / 通知栏 / 快捷方式 / 硬件键**：录音开始、停止、标记能否在锁屏完成；
  现有按键映射要与之统一，避免冲突。
- **Doze / 厂商省电**：后台同步和上传会被杀；需要调度（JobScheduler/前台服务）
  与"电池优化白名单"引导。
- **录音格式**：设备默认 m4a（体积小），引擎要 16k mono wav → 服务端转码；
  可选"高保真直录 wav"（省转码、费空间）。要定默认与切换点。
- **超长录音 / 中断续录**：`MAX_REC_SEC` 到点自动停；将来分段录音的拼接、时间轴、
  文件命名与同步都要定。
- **卸载重装**：`allowBackup=false`，本地库丢失；公共音频还在、服务器有副本。
  重装后的恢复路径（扫目录 + 服务器全量回填 + 去重）必须有。
- **多设备同录**：同一时刻两台手机录音 → 两条记录；不要靠文件名/时间合并。

## 3. 音频与转写质量

- **解码依赖**：服务端转码依赖 ffmpeg/av；不同容器、编码、损坏文件；启动时自检并
  给出"转码不可用"的显式状态，而不是任务失败。
- **VAD/静音预检**：入队前先看时长/能量/是否静音，避免把 3 小时静音丢给引擎；
  空结果要有专门错误码与文案。
- **长音频**：引擎上下文/窗口限制（Whisper 30 秒窗口、Qwen 上下文）、云 API 常见
  单文件上限（约 25MB）。建议按 VAD 切片 + 段偏移合并；切片边界重叠避免吞字。
- **语言**：中文为主，但会议里常中英混说；`auto` 在短音频上容易判错。
  建议默认 `zh`，支持按条指定，逐句语言先不做。
- **热词/术语表**：人名、项目名、专业词识别差；可用 prompt 注入词表；
  是否把"用户改过的词"自动进词表，需要产品决定。
- **标点/数字/单位/大小写**：各引擎差异大；建议轻量规范化，但保留引擎原文可回看。
- **幻觉与重复**：Whisper 在静音/噪音上会编内容、重复循环；建议规则 + 置信度检测，
  **标记低置信/可疑段，不自动删**，让人确认。
- **说话人**：不同尝试的 `spk` 编号不可比（同一人可能换号）；切版后发言人色片会变。
  人工改说话人锚定在时间区间；是否支持"给发言人命名（A/B）并跨记录复用"要定（建议先不做）。
- **导入的外部文稿**：作为一次尝试（`source=import`，质量档最低）还是只读备注？
  要和"可升级"策略对齐，否则会出现两份互不相干的正文。

## 4. 人工修订与尝试（规则只写了原则，缺算法）

- **重挂接**：新尝试与旧修订按时间重叠匹配；阈值多少？重叠多个句怎么办？
  拆分/合并句、整段删除、插入新句分别怎么映射？需要一张明确的规则表。
- **修订的基准**：`edits` 要不要记"基于哪个 attempt、哪句原文、原文 hash"；
  切尝试后如何展示"这句改自旧稿"；低置信时如何提示。
- **修订冲突**：两台设备同时改同一句（或改同一时间区间）怎么合并？
  建议：同一句 LWW + 保留双方历史；不同区间各自生效。
- **修订与删除**：删除句是墓碑还是物理删？重转写后删除意图要不要保留？
- **撤销/重做**：逐句编辑是否需要 undo；跨同步的撤销怎么定义（再发一个反向 op）。

## 5. 搜索与索引

- **索引哪一版**：只索引生效稿 + 人工修订，还是所有尝试？建议只索引生效稿，
  切指针后重建该记录；旧尝试不参与搜索，避免"搜到一份没在看的稿"。
- **中文分词**：现有 FTS 用 2-gram；要定是否升级（词典/SQLite 分词器不可用时的方案）。
- **搜索结果**：高亮命中句、跳转后定位到句与时间；跨尝试切换后结果失效的处理。
- **搜索范围**：标题/正文/标签/标记/时间；排序（相关度 vs 时间）；分页。
- **重建成本**：FTS 重建/增量更新的时机（编辑、切版、迁移）；失败时的降级（LIKE）。
- **大库性能**：1k/10k 记录的索引大小、查询延迟、写入放大。

## 6. 同步协议边界（细节未穷举）

- **rev 粒度**：records / jobs / attempts / edits 共用一个全局变更序列，还是各自 rev？
  建议一个全局 `changes(rev)`，事务内写入，客户端游标只认它。
- **游标过期**：changes 只保留 N 天；设备离线很久回来后 cursor 太旧。
  用 `GET /sync/manifest`（id/rev/deleted/sync_hash，分页）做状态对账兜底：
  先推 outbox，再按清单拉差异、删幽灵、更新游标；不依赖历史保留期。
  记录数到 10 万+ 再升级 Merkle 树。详见 `架构设计.md` §5.6。
- **冲突规则穷举**：删除 vs 改名、删除 vs 上传、删除 vs 钉指针、同句修订并发、
  两台设备同时删/同时改；每条写出"谁赢、怎么提示、能否恢复"。
- **outbox 依赖**：改名/删除/重转的先后顺序；同一记录的操作要串行，不同记录可并行；
  失败不能阻塞其他记录；重试要带指数退避 + 抖动。
- **重放窗口**：op_id 去重保留多久（建议与 changes 同寿命）；客户端重装后旧 op 重放。
- **上传与删除竞态**：上传中途被删、删除后又有旧请求到达；用墓碑 + 录音 hash 查重，
  返回明确状态（已删除/已存在）。
- **断点续传细节**：分块大小、并发、校验、失败清理、URI 过期；服务端合并临时文件；
  P2 再做，但接口要预留。
- **弱网/切换网络**：上传中 WiFi↔4G；"仅 WiFi 上传"开关；失败重试边界；流量提示。
- **后台同步**：App 退到后台后的调度（前台服务/JobScheduler）；Doze 白名单；
  与"录音不停"共用同一个前台服务。
- **限流/背压**：服务端并发上传、队列上限、磁盘水位；满了是拒绝新上传还是排队，
  要给用户明确状态（不是 500）。
- **SSE 断线恢复**：`Last-Event-ID` 重放窗口、去重；移动端是否用 SSE（建议长轮询兜底）。
- **版本协商**：v1/v2、App 最低版本、能力位（支持哪些 ops/尝试/直连）、
  老 App 连新服务器的降级路径。

## 7. 多设备与多库房

- **同一录音去重**：两台设备传同一文件（hash 相同）→ 一条记录还是两条？
  建议音频按 hash 复用，记录仍按来源分开（或合并需明确产品规则）。
- **多设备身份**：一机一令牌、吊销、重装后是否复用设备 id；
  设备名冲突；多台同名设备怎么区分。
- **库房复制内容**：changes 表是否复制？音频复制范围（全量/仅最近）？
  备份不完整时接管会丢什么；需要"备份完整性检查"。
- **epoch 冲突**：老库房在分裂期间写入的数据怎么处理（丢弃？手工合并？）；
  建议：老库房降级为客户端后，它的本地改动作为普通 ops 重放，冲突按规则处理。
- **中转语义**：中转是否存音频、存多久、如何确认"已转交"、失败重试、加密；
  中转被偷/丢失的风险。
- **手机直连引擎的信任**：手机拿到的是引擎令牌还是库房签发的短时令牌；
  直连后结果如何回传（outbox 尝试）；引擎不在同一网络时怎么办。

## 8. 存储、容量、备份、迁移

- **音频保留**：现有 `retention_audio: keep|compact` 是预留，语义未定。
  要定：转写后是否删本地音频、服务端保留多久、归档到冷存储、按条/全局策略。
- **尝试清理**：保留几个版本、多久、是否受"用户钉住"保护；清理后指针指向它怎么办。
- **容量与配额**：磁盘水位告警、上传拒绝阈值、模型占用、备份占用；
  1 小时录音 ~14MB，100 小时 ~1.4GB，要算清楚。
- **备份与恢复**：备份内容（DB + 音频 + 配置，不含日志）、频率、加密、保留代数；
  **恢复演练**必须做；接管前校验备份完整。
- **彻底删除**：墓碑 GC 后音频/导出/备份里的副本何时清；"立即彻底删除"按钮；
  删除后旧设备再上传同一录音怎么办（hash 黑名单还是允许重新出现）。
- **数据库维护**：WAL 增长、checkpoint、VACUUM、索引体积、schema 版本与迁移回滚。
- **文件系统坑**：Windows 文件锁、长路径、Unicode 文件名、大小写、NAS/SMB 延迟、
  原子写与 fsync；共享目录场景下"谁写谁读"。
- **迁移（已决定放弃）**：2026-10-26 拍板**破坏性重建、不迁移历史数据**；不需要迁移脚本、
  hash 补算、解析对账。只需：先备份旧 `data/`、`/sdcard/s1rec/`、`app-state`，新版本空库启动；
  旧文件保留原位，确认无误后再手动清理。
- **App 端整库导出/导入**：现在完全没有（`State.java` 注释也承认）；换机/卸载是刚需；
  至少导出 zip（DB + 音频清单 + 分类/标记），导入时去重。
- **契约文档**：`数据契约.md` 与实现已不一致，要随新结构重写（或标记为 v2）；
  导出格式版本号；旧版保留 30 天的承诺要落到脚本。

## 9. 安全与隐私（威胁模型还没写）

- **明文局域网**：录音和转写稿在 LAN 上明文传输；建议默认提示风险，支持自签 TLS +
  指纹校验；跨公网强制加密。
- **配对二维码**：含令牌，截图/拍照泄露；建议短期一次性配对码或首次确认。
- **令牌管理**：一机一令牌、吊销、轮换、过期；控制台会话鉴权；CORS/CSRF。
- **SSRF**：库房允许配置任意引擎 URL → 可被用来访问内网服务；要限制协议/网段/
  重定向，并对返回大小/类型做校验。
- **恶意输入**：超大上传、畸形音频、路径穿越、引擎返回超大/非法 JSON、
  压缩炸弹；需要大小上限、类型校验、超时、隔离。
- **手机直连引擎**：令牌最小权限、可撤销、只允许转写；不要复用库房管理令牌。
- **日志与诊断**：日志里不能出现正文/令牌；诊断包要脱敏；崩溃上报是否自托管。
- **云端/AI 出网审计**：哪些录音去过云端、发给了哪个模型；本地模式开关；
  给用户"这条出过网"的标记。
- **备份加密**：备份含全部录音与正文，落盘要加密或至少权限隔离。
- **模型供应链**：下载源、哈希校验、版本固定、失败回滚；不要静默换模型。
- **录音法律合规**：部分场景需征得对方同意；产品上是否有提示，需要你判断。

## 10. 运维、发布、版本兼容

- **开机自启 / 服务化**：Windows 服务或计划任务、Docker restart 策略；
  库房断电恢复后自动起 worker。
- **升级**：服务端升级时正在跑的任务怎么办；DB 迁移加锁；回滚；
  App 与服务器版本兼容矩阵；最低支持版本。
- **监控**：磁盘、队列、失败率、引擎在线、备份是否成功；告警渠道（桌面通知/邮件）。
- **日志**：轮转、保留、隐私脱敏；诊断包导出。
- **配置管理**：设置项散落（控制台/环境变量/DB/文件），要有一处权威清单与默认值。
- **网络**：端口冲突、防火墙、双网卡、IPv6、mDNS 发现、VPN/虚拟组网地址选择。
- **时钟同步**：库房/强机/手机都建议 NTP；时间偏差对"最近/今天"展示的影响。
- **引擎服务生命周期**：模型常驻还是按需加载、切换模型的冷启动（可能几分钟）、
  GPU 被其他程序占用、显存不足降级、引擎进程崩溃自愈。

- **夹具**：静音/噪音/多人/长音频/损坏文件/中英混说/极端时钟；

- **端到端**：[目标流程 §10](../流程/目标流程.md) 的 5 个任务脚本，临时数据目录一键跑；
- **备份恢复演练**：从备份接管一次，验证记录/修订/标记/音频数量一致。

- 编辑：撤销/重做、保存时机、输入法遮挡、长按选择；
- 分类管理：重命名/合并/删除对记录的影响；跨端按名字匹配的重名问题；
- 排序/筛选状态保持、搜索防抖、分页体验；
- 无障碍（TalkBack/字号/对比度）、深色模式、720×1280 小屏、横屏；
- 硬件键/媒体键在不同 ROM 的行为差异；
- 通知权限（13+）与前台服务类型（14+）的引导。
