# 设计手册：从"功能拼装"到"一条主路径"

> 2026-10-26。给 voxnote 重设计用，也适用于下一个项目。
> 回答两个问题：为什么"每个功能都对，合起来难用"；怎么设计才顺。

## 0. 一句话

**软件不是功能列表，是"从想法到结果的一条路"。**
功能是零件，体验是路。你现在的项目零件都造出来了，但没人负责修路。

## 1. 为什么会出现"功能都对，用起来磕磕绊绊"

逐条对照 voxnote 的现状（证据见 [DIAGNOSIS.md](DIAGNOSIS.md)）：

1. **按"功能"设计，而不是按"任务"设计。**
   每想到一个能力就加一个入口（同步、转写、云端、录音流、AI、批量…），
   每个入口单独看都合理，合起来就是"零件仓库"，用户不知道该从哪进。
2. **只设计了成功路径，没设计状态空间。**
   功能定义的是"成功时发生什么"；没人定义"没网/没权限/引擎坏了/重复上传/删除/旧数据"时发生什么。
   实际使用中 80% 的磕碰都发生在这条没设计的路上：静默停在 raw、失败不显示、删了又回来。
3. **数据模型被功能牵着走（顺序反了）。**
   每加一个功能就在旁边存一份数据（md、app-state、SharedPreferences、服务器库、镜像），
   于是"改名/删除/转写"在界面上表现为"改了又变、不知道哪步"。
   正确顺序是 **数据 → 状态 → 交互 → 界面**，不是界面 → 功能 → 补数据。
4. **没有"唯一主线"，每个功能都想当主角。**
   同步要求进设置页、转写要求一个按钮、云端要求单独一页——
   结果没有主角，用户每一次都要重新判断"这事该去哪做"。
5. **没有取舍机制。**
   "想到的功能"不等于"该做的功能"。没有准入标准、没有删除机制，功能只增不减，
   复杂度是乘法增长，不是加法。
6. **验收标准是"能跑"，不是"用户能顺畅完成"。**
   所以永远发现不了磕碰：开发时走的是自己脑中的路径，不是用户第一次走的路径。
7. **局部最优堆成全局最差。** 4 天 149 次提交，每次单看都对；
   但没有一个环节负责"全局只有一条路、一套状态、一处真相"。

一句话：**不是你不会写功能，是没人负责"路"和"状态"。这两件事不写代码，靠设计。**

## 2. 设计一个软件的正确顺序

```
错误顺序（项目现状）：界面 → 功能 → 发现不够 → 补数据 → 补同步 → 再补界面
正确顺序：          一句话与主线 → 数据（唯一真相） → 状态机 → 路径与界面 → 验证 → 迭代
```

五步，每步都有产出物，做完才进下一步：

### 第 1 步：一页纸

必须能写满这一页，写不满说明还没想清楚：

```
产品一句话：____________（谁，在什么场景，解决什么）
唯一主线：  ____________（用户 80% 时间只做这一件事）
三个核心任务：1.______  2.______  3.______
明确不做（这一版）：____________
```

voxnote 示例：
- 一句话：给"每天说很多话的人"一个按一下就能录、能读、能搜的本地笔记；
- 主线：**录 → 自动上传/转写 → 读 → 改 → 找**；
- 核心任务：① 录一条并看到转写；② 找到上周某句话；③ 改几句并让所有设备一致；
- 这一版不做：AI 问答、录音流、多引擎切换、批量管理、云端独立页。

### 第 2 步：数据先行（唯一真相）

列实体，每个实体写清"唯一存在哪里、谁能改、怎么算改过"：

| 实体 | 唯一真相 | 谁写 | 版本/冲突 |
| --- | --- | --- | --- |
| 录音 | 音频文件 + 记录行 | 手机 | record rev |
| 转写稿 | 不可变"尝试" | 库房/远程引擎/手机云 | 只增 + 生效指针 |
| 人工修订 | edits 表 | 手机/控制台 | 字段级、按时间锚定 |
| 标题/分类/标记 | records 行 | 两端 | 字段级 LWW |
| 任务 | jobs 表 | 库房 | 状态机 |

**一条事实只存一处**，其余都是导出/缓存。做这一步时先别想界面。

### 第 3 步：状态机（体验的核心）

每个实体只画一遍：状态、谁能触发、失败去哪、怎么恢复。

```
录好的记录：仅本机 → 待上传 → 排队中 → 转写中 36% → 已转写（快稿/精稿）
                    ↘ 失败（原因 + 下一步）     ↘ 删除（墓碑）
```

规矩：
- **一条记录只暴露一个状态**（内部可以有三个维度，展示层翻译成一个）；
- **每个失败状态必须有下一步**（重试/换引擎/看原因/清理空间）；
- 状态词全端统一（手机、控制台、服务端用同一套中文）。

### 第 4 步：路径与界面（最后画）

主线每一步 = 一屏、一个主按钮、一个状态。填写这张表：

| 步骤 | 用户意图 | 入口 | 成功 | 空态 | 失败 + 下一步 |
| --- | --- | --- | --- | --- | --- |
| 录 | 现在开始记 | 首页大按钮 | 卡片出现、开始上传 | "还没录过" | 录音失败→重试/检查权限 |
| 转 | 想知道说了什么 | 自动（无需操作） | 快稿几秒出现 | "还没转写" | 引擎未就绪→去设置下载模型 |
| 同步 | 别的设备也能看 | 自动 + 顶部状态条 | 状态变已同步 | — | 连不上→排队/切换地址/看原因 |

每屏必须写**四态**：正常 / 空 / 加载 / 失败（+ 离线、冲突）。
写不出来的地方，就是以后会磕碰的地方。

### 第 5 步：验证（不是问好不好看）

- 写 5 个"任务脚本"（见 §4），找 3 个没看过的人，只给任务不给说明；
- 记录卡点：卡住 >30 秒、问"这是干嘛的"、点错两次以上 = 必须改；
- 改完再跑一遍主线；**一个功能上线前，主线必须仍然一遍走通**。

## 3. 功能准入表（防止越做越乱）

每想到一个功能，先填这 4 个问题，过不了就不做/延后：

| 问题 | 不合格的表现 |
| --- | --- |
| 它服务主线哪一步？ | 答不上来 → 不做 |
| 它新增几个入口/状态/设置项？ | >1 个入口 → 先合并 |
| 不做会怎样？ | "也没什么" → 延后 |
| 能不能做成默认行为，而不是一个开关？ | 需要用户理解的概念 → 改成默认或砍 |

配套规矩：**每加 1 个功能，砍 1 个或延后 1 个。** 功能总数封顶，复杂度才可控。

## 4. 验证"流畅"的任务脚本（voxnote 版）

不测功能，测任务；不追求全过，只记录卡点：

1. **第一次用**：给你手机和服务器地址，配对成功并转出一条录音。
2. **断网**：飞行模式录一条 → 关飞行模式 → 它自己传上去并出稿。
3. **失败恢复**：故意让服务器引擎不可用 → 用户能看出"为什么没转"并修好。
4. **一致性**：手机上改个标题、删一条录音 → 控制台刷新后一致，且不会复活。
5. **找东西**：一周后，不用分类，靠搜索找到"那句关于门禁的话"。

判定：每项 ≤3 分钟、无需解释、失败时知道点哪 = 流畅；否则回到 §2 第 4 步改路径。

## 5. 落到 voxnote 的具体建议

- **先做减法**：v1 只保留 `录 / 列表 / 详情 / 自动转写 / 同步 / 搜索 / 改名分类`；
  录音流、AI、批量、多引擎切换、云端独立页先隐藏或删除，等主线顺了再加。
- **先修数据与状态**，再修界面：尝试/指针、墓碑、状态机、outbox（见 [REDESIGN.md](REDESIGN.md)）；
- **一次只加一个功能**，加完跑 §4 的 5 个脚本；
- **维护两张清单**：`做` 和 `不做`（"不做清单"要写原因，防止反复纠结）。

## 6. 日常习惯（比方法更重要）

- 每次写代码前先问：**这一步属于哪条主线的哪一步？**
- 每次想加设置项先问：**能不能变成默认行为？** 设置项是设计债。
- 每次加功能先问：**它会让状态/入口变多吗？** 会 → 先简化再加。
- 每周跑一次 §4 的脚本，记录卡点；卡点不清零，不加新功能。
- 体验问题优先修"失败路径"和"一致性"，这两类最伤信任。

## 7. 记住三句话

1. **设计不是画界面，是决定"不做什么"和"状态怎么走"。**
2. **用户感知到的不是功能数量，是路径长度和失败时的无助感。**
3. **一条主线、一套状态、一处真相——做到这三件，软件自然顺。**
