## 1. 设计目标

### 1.1 体验目标（可验收）

| 目标 | 判定方式 |
| --- | --- |
| 每次操作都有即时反馈 | 点「转写/同步/删除」≤200ms 出现明确状态，不是 toast 后无下文 |
| 失败必须可行动 | 100% 失败有：人话原因 + 下一步动作（重试/换引擎/下载模型/转格式） |
| 转写全程可见 | 排队位置、百分比、阶段（载模型/解码/转写）、耗时、引擎，手机与控制台一致 |
| 同步可解释 | 每台设备、每条记录都能回答"上次成功是什么时候、还差什么、为什么失败" |
| 增量而非全量 | 一条记录变化只更新这一条；不再有"改一个字重扫全库" |
| 删除与改名双向一致 | 一轮同步内两端一致，不复活 |
| 多来源不打架 | 库房/远程引擎/手机云的稿共存可切换，人工修订不丢；同一记录不会因"谁后转"被覆盖 |
| 规模可用 | 1k 记录 / 100 小时音频：列表冷启动 <1s，详情 <300ms，增量拉取 <300ms/轮 |

### 1.2 技术约束（保持不变）

- Android：纯 Java、无 Gradle、**无第三方依赖**、单 Activity 可拆但不引框架；
  目标机 Android 8.1（API 27），兼容 12+；数据目录 `/sdcard/s1rec/` 旧名保留，要动就写迁移。
- 服务端：FastAPI + SQLite 单进程；音频文件是真归档；`data/` 可整目录拷走；
  控制台自托管、离线可用（vendor 第三方库）。
- 不变量：**机器派生可无限重放；人写内容永不被覆盖**；导入来源的物理文件永不改写。
- 隐私：日志/数据库/录音不进仓库（现状已满足）。

### 1.3 设计原则

1. **一个事实只存一处**，其余全是派生/导出。
2. **状态显式化**：能用枚举表达的就不要"从文件推断"。
3. **先可解释，再快**：任何自动行为都要留下可查记录。
4. **增量优先**：协议、存储、渲染三层都按增量设计。
5. **可重建**：本机库可从音频+导出物重建（迁移/换机/恢复）。
6. **派生结果可多份、不可丢**：转写允许多来源多版本（尝试），但只切"生效"，绝不覆盖删除（§6.5）。

## 2. 目标架构

```
┌────────────── Android App ──────────────┐        ┌────────────── voxnote server ──────────────┐
│ UI                                        │        │ Web 控制台（SSE 事件流 + 列表虚拟化）        │
│  列表 / 详情 / 同步中心 / 设置 / 诊断       │        │                                            │
│        ↑ 只读 RecordStore + 观察者         │        │                                            │
│ RecordStore (SQLite, framework)           │        │ RecordService：rev / 墓碑 / 人机分层         │
│  records · segments · jobs · outbox ·     │ HTTPS  │ Queue：jobs（优先级/取消/阶段进度）           │
│  sync_state                               │ ←────→ │ Engines：readiness + 模型管理                │
│ SyncEngine：outbox 推送 + 游标拉取 + 重试    │        │ SQLite（工作真相）+ audio 归档 + 导出镜像     │
│ 录音端：文件归档（Storage/导入插件不动）     │        │                                            │
└───────────────────────────────────────────┘        └────────────────────────────────────────────┘
```

关键变化：

- **工作真相 = 两端各自的本地库**；音频文件与 md/jsonl 是**归档与导出**，不再被反解析成事实。
- 服务端 `records.rev` 单调递增；客户端按游标拉**变更流**（含墓碑、任务状态），在事务里应用。
- 手机端不再有"第二套转写路径"：转写只发生在服务端，手机是观察者 + 触发者。
- 所有失败落 `error_code + error_hint`，两端同一套文案与动作。

## 3. 数据模型

### 3.1 标识与时间

- `id`：UUIDv7（时间有序，字符串）——稳定、可离线生成、不依赖设备时钟精确；
- `legacy_id`：`yyyyMMdd_HHmmss[-N]`，只用于迁移与文件名兼容，不再作为主键语义；
- `recorded_at`：毫秒（录音内时间轴基准）；
- `audio_sha256`：上传前本地算一次，服务端唯一索引 → 幂等与去重；
- 逐句 `seg_id`：服务端生成的稳定 ID（迁移时沿用 `segments.id`），客户端不重算。

### 3.2 服务端表（草案，迁移为增量 ALTER）

```
records(
  id TEXT PK, rev INTEGER NOT NULL,          -- rev 全局单调（见 records_rev 序列表）
  legacy_id TEXT, deleted_at INTEGER,        -- 墓碑
  title, cat, mode, src, device_id,
  recorded_at INTEGER, dur_ms INTEGER, bytes INTEGER,
  audio_path, audio_name, audio_sha256 TEXT UNIQUE,
  status TEXT,                               -- 统一生命周期，见 §4
  active_attempt_id TEXT, active_pinned INTEGER,  -- 哪次转写生效（§6.5）
  engine, error_code, error_hint,
  created_at, updated_at)

records_rev(seq INTEGER PK AUTOINCREMENT, record_id, rev)   -- 变更流真源（保留 N 天）

-- 转写尝试：只增不改，多个来源（库房/远程引擎/手机云）各写各的，互不覆盖
transcript_attempts(
  id TEXT PK, record_id, rev,
  audio_sha256, source TEXT,        -- hub | engine | phone | cloud
  engine, model, params_hash,       -- 幂等键：record+sha+source+engine+params
  quality_tier INTEGER,             -- 3=云/远程大模型, 2=库房小模型, 1=手机小模型
  cost_hint TEXT, duration_ms INTEGER, created_at INTEGER,
  UNIQUE(record_id, audio_sha256, source, engine, params_hash))

attempt_segments(attempt_id, idx, t_ms, e_ms, text, spk)   -- 机器层，属于某次尝试

-- 人工层：挂在时间区间上，换哪次尝试都不丢
edits(
  id TEXT PK, record_id, rev,
  anchor_t_ms, anchor_e_ms,        -- 锚定原句时间区间
  original_hash TEXT,              -- 原句文本哈希，用于重挂接校验
  text, spk, deleted INTEGER, edited_at INTEGER)

jobs(
  id, record_id, engine, source, state, stage, progress,
  error_code, error_hint, priority, cancel_requested,
  queued_at, started_at, finished_at)

devices(
  id, name, app_version, last_seen_at, last_cursor, status)

engines(
  id, kind, name, url, token, model,
  quality_tier, slots, timeout_ms, enabled)
```

变更流查询（核心）：

```sql
SELECT r.* FROM records r WHERE r.rev > :cursor ORDER BY r.rev LIMIT :n;
-- job 状态另表按 updated_rev 索引，或并入同一 rev 序列（推荐：jobs 也有 rev，统一消费）
```

### 3.3 客户端表（Android framework SQLite，草案）

```
records(id PK, server_rev, local_dirty INTEGER, deleted INTEGER,
        title, cat, marks_json, recorded_at, dur_ms,
        audio_path, audio_uri, audio_sha256, status, engine,
        active_attempt_id, active_pinned, pending_upgrade INTEGER,
        error_code, error_hint, updated_at)

attempts(id PK, record_id, source, engine, model, quality_tier,
         segments_json, created_at, synced INTEGER)
  -- 本地也可能先产生尝试（手机云转写），联网后上传；不可变

edits(id PK, record_id, anchor_t_ms, anchor_e_ms, original_hash,
      text, spk, deleted, edited_at, dirty INTEGER)
  -- 人工层：只增/改，跨尝试复用

jobs(record_id PK, job_id, source, state, stage, progress, error_code, error_hint, updated_at)

outbox(op_id PK, kind, record_id, payload_json, base_rev,
       created_at, attempts, next_retry_at, last_error)
  -- kind: upload_audio / patch_meta / delete / retranscribe / upload_attempt / patch_edit

sync_state(k PK, v)   -- cursor / last_pull_at / last_push_at / device_id / epoch
```

`outbox` 是"手机上做的动作"的唯一出口：UI 只写本地库 + outbox，SyncEngine 负责幂等推送；
推送成功才清，失败按退避重试。**离线可用**成为自然结果。

### 3.4 人机分层（在多来源下强化）

- **机器层属于"尝试"**：每次转写 = 一条不可变的 `attempt`，带自己的句和时间轴；
  重转写不是覆盖，而是新增一条尝试、移动 `active_attempt_id`（§6.5）；
- **人工层挂在时间区间上**：`edits` 用 `(anchor_t_ms, anchor_e_ms, original_hash)` 锚定，
  读取生效稿时按时间重叠套到当前生效尝试上；
- 生效稿 = `active attempt 的句` + 按重叠套用 `edits`；人工修改永远不会被任何一次转写覆盖；
- **重挂接**：新尝试与旧锚点重叠度过低时，界面提示"这句修订基于旧稿，可能错位"，
  允许确认/丢弃，而不是静默挪位置；
- 契约文档补齐真实实现：`index.jsonl / record.json / segments.jsonl / edits.jsonl` 要么实现、
  要么从契约里删掉，换成"SQLite + 导出格式"。

### 3.5 删除语义（统一）

**默认只做标记，不动源文件**；释放空间是独立的清理动作。

| 来源 | 删除动作 | 清理动作（设置页 → 存储管理） |
| --- | --- | --- |
| 自录音频 | 记墓碑 + UI/数据库标记，**不删文件** | 用户确认后删除音频/导出 |
| 导入来源（厂商） | 只记墓碑，物理文件永不改 | 不适用（原始文件不归我们管） |
| 服务端删除 | 记墓碑 → 变更流下发；设备隐藏 | 两端"存储管理"统一清理 |
| 墓碑/版本 GC | 默认不自动清；清理动作前一直可恢复 | 清理已删除记录、旧尝试、临时文件、备份旧代 |

## 4. 统一状态机（两端同一套）

```
record:
  local_only ──upload──▶ uploaded ──enqueue──▶ queued ──▶ transcribing(p) ──▶ transcribed
       │                    │                     │              │              │
       │                    │                     │              │        （快稿/精稿由 attempt 决定）
       │                    └────────── fail ◀────┴──────────────┘
       │                                 (error_code + hint)
       └──▶ deleted（墓碑，任意状态可达）

展示层把"已转写"再细分成：已转写（快稿 · 可升级） / 已转写（精稿）
人工层同步单独一维： clean / dirty / conflict
```

- 手机卡片只显示**一个**流程 chip：`仅本机 / 待上传 / 排队 2 / 转写 36% / 已转写（快稿）/ 已转写 / 失败：原因 / 已删除`。
- 失败 chip 点开 = 原因 + 动作，不再有"上传失败但不说为什么"。
- 服务端 `records.status` 与 `jobs.state` 保持职责分离：record 是结果，job 是过程；
  客户端把两者**合并成一个可展示状态**，而不是各自一套。
- "更准的稿到了"不是状态回退，而是同一个"已转写"下的质量升级（§6.5）。

## 5. 同步协议 v2（草案）

### 5.1 设计要点

| 语义 | v1 现状 | v2 |
| --- | --- | --- |
| 变更识别 | `updated_at`（毫秒，可能同值） | `rev` 单调递增 |
| 删除 | 无 | 墓碑进变更流 |
| 分页 | `LIMIT 500` 无续取 | `next_cursor + has_more` |
| 幂等 | 声称有，实际生成 `-2` | `Idempotency-Key` + `audio_sha256` 唯一 |
| 断点 | 无 | 分块/续传 + 校验 |
| 任务状态 | 设备不可见 | job 变更进同一变更流 |
| 转写结果 | 每次整篇拉、整层覆盖 | **不可变"转写尝试" + 生效指针**（见 §6.5） |
| 本地动作 | 各自 HTTP 直接发 | `outbox` 批量 ops，幂等、可重放 |

### 5.2 端点草案（`/api/v2`）

```
GET    /sync/changes?cursor=&limit=200
       → {changes:[{rev, kind:"record"|"job", deleted?,
                    record?:{...}, active_attempt?:{id,quality,source},
                    job?:{state,stage,progress,error_code,error_hint}}],
          next_cursor, has_more, server_time}
       · has_more=true 时必须继续拉，直到追平
       · 只带"这一轮真的变了"的字段，不做全表快照

GET    /records/{id}/transcripts          → 尝试列表（id/来源/引擎/质量档/时间/大小）
GET    /records/{id}/transcripts/{aid}    → 某次尝试的 NDJSON（**不可变，可永久缓存**）
POST   /records/{id}/transcripts          {source, engine, model, params, segments, audio_sha256}
       → 201 {attempt_id}；幂等键 = record_id+audio_sha256+source+engine+params
POST   /records/{id}/active-transcript    {attempt_id | policy:auto} → 切换生效稿
POST   /sync/upload                        multipart(meta, file)
       Header: Idempotency-Key: <device_id>:<legacy_id>
       meta: {legacy_id, recorded_at, dur_ms, audio_sha256, title, cat, marks, mode}
       → 201 {id, rev} | 200 {id, rev, existing:true}
       · 同 sha256 已存在 → 复用音频，只关联；绝不生成 -2 副本
       · 支持 Content-Range 分块，续传按 sha256 校验

POST   /sync/ops                           {ops:[{op_id, kind, record_id, base_rev, payload}]}
       kinds: patch_meta / delete / retranscribe / patch_edit / pin_attempt
       → {results:[{op_id, ok, applied_rev?, conflict?}]}
       · op_id 幂等；base_rev 用于字段级 LWW 与冲突回传

DELETE /sync/records/{id}              → 墓碑（等价于 delete op，保留给简单客户端）
POST   /records/{id}/transcribe        {engine?} → {job_id}；活跃 job 复用
GET    /sync/diagnostics               → 设备游标、待处理数、服务端就绪状态
GET    /events                         SSE：job/record 变更（控制台用；手机可选）
```

### 5.3 冲突规则（写死，可解释）

- 字段级 LWW：`title / cat / marks` 以**服务端 rev** 排序，同一字段两端并发改 → 后到者胜；
- 每次覆盖都进 `ops` 历史（可回看"谁在什么时候改成了什么"）；
- 人工层（逐句修订）不与机器层比较：重转写永远不覆盖；
- **机器层不参与 LWW**：多次转写是"追加尝试 + 切指针"，不是覆盖一篇稿子——所以
  库房、远程引擎、手机云同时产出也不会互相盖掉（详见 §6.5）；
- 手机优先只是默认策略，不再散落在代码注释里。

### 5.4 兼容与迁移

- v1 端点保留一个版本周期，标记 deprecated；旧 App 仍可推/拉，但不参与 v2 的墓碑/幂等语义；
- **不迁移旧数据**（2026-10-26 决策）：新版本从空库开始，旧 md/app-state/旧库不导入；
  旧文件保留在原位置，建议用户先自行备份；不做 `legacy_id` 映射与双写。

## 6. 转写子系统

### 6.1 引擎就绪（readiness）

```python
class Engine:
    def ready(self) -> tuple[bool, dict]:
        # 依赖可 import + 模型文件存在且大小/哈希正确 + 一次轻量自检（可选）
        # 返回 {ok, reasons:[...], models:[...], device:"cpu|cuda"}
```

- `/engines` 返回 `ready / detail / models / device`；控制台设置页直接显示"未就绪：缺模型 xxx"；
- 手机端只显示服务器就绪状态（不猜测、不本地判定）；
- `enqueue_default` 在未就绪时**落一个显式状态**（`status=raw, error_code=ENGINE_NOT_READY`），
  不再静默返回 0。手动触发时返回可执行的原因。

### 6.2 任务队列

- 优先级：手动重转写 > 录音自动转写 > 批量重转写；同优先级 FIFO；
- 阶段进度：`loading_model → decoding → transcribing(p) → finalizing`（前端可显示"正在加载模型"）；
- 取消：控制台 + 手机都能取消 queued；running 取消 = 置标记，引擎在句边界退出；
- ETA：按本机 RTF 滑动平均估计，显示"约 2 分钟"，不承诺精确；
- 失败重试：可重试错误指数退避（1/5/15 分钟，最多 N 次），不可重试直接 fail + hint。

### 6.3 错误码体系（两端同一份）

| code | 人话 | 动作 |
| --- | --- | --- |
| AUDIO_DECODE | 音频解不开 | 转 16k wav 重试 / 检查文件 |
| AUDIO_MISSING | 音频不在了 | 从设备重传 |
| ENGINE_NOT_READY / MODEL_MISSING | 引擎没准备好 | 去设置下载模型 / 换引擎 |
| GPU_RUNTIME | 显卡运行库缺失 | 切 CPU 重试 |
| EMPTY_RESULT | 没识别到语音 | 确认不是静音；可重试 |
| TIMEOUT | 超时 | 重试 / 换云端引擎 |
| CLOUD_AUTH / CLOUD_QUOTA | Key 无效 / 配额用尽 | 改 Key / 等额度 |
| STORAGE_FULL / PERMISSION | 磁盘或权限问题 | 清理空间 / 改路径 |
| INTERNAL | 未归类 | 重试 + 展开原始异常 + 导出诊断 |

分类规则改成**先看异常类型（PermissionError/OSError）再看因果链关键词**，不允许只靠子串。

### 6.4 增量落库与实时

- 转写中：内存累积 + 每 2–3 秒把"脏区间"写库（不再 DELETE 全表）；镜像文件只在完成时写；
- 完成时新增一条**不可变尝试**并移动生效指针；变更流只带"指针变了/有新尝试"的小消息；
- 手机/控制台按 `attempt_id` 拉稿：尝试不可变 → 可永久缓存，换指针不用重新下载全文；
- 控制台 SSE 推送进度与新增句；手机前台用 changes 拉取（10 秒，可见时加速，后台退避）；
- 打字机效果只用于"新增的句"，不重建已读内容（保护滚动位置）。

### 6.5 多来源转写：尝试 + 生效指针

问题：库房、远程引擎、手机（直连云）都能出稿，精度/成本/延迟不同。如果还是"一条记录一份稿、
整层覆盖"，就会互相覆盖，同步永远对不上。

做法：**把转写结果从"一份稿"改成"多次尝试 + 一个生效指针"**。

- `transcript_attempt`（只增不改）：`id / record_id / audio_sha256 / source(hub|engine|phone|cloud) /
  engine / model / params_hash / quality_tier / cost_hint / segments / created_at / duration_ms`；
- 幂等键 `(record_id, audio_sha256, source, engine, params_hash)`：同一份音频同配置重跑不产生重复；
- 记录的 `active_attempt_id` 是**唯一会变的字段**，跟 `rev` 走；切错了随时切回，旧稿永远在；
- **质量档**（默认排序）：云端/远程大模型（T3）> 库房小模型（T2）> 手机端/离线小模型（T1）。
  但"最准"不等于"最该用"：成本、隐私、等待时间都算，默认策略是**先出快稿、再按规则升级**；
- **确定性策略**（所有端算出来一致，不需要协商）：`rank = (pinned, quality_tier, created_at)`；
  用户手动钉住的优先，否则取最高档、同档取最新。库房离线时手机按同一规则本地计算；
  联网后以库房指针为准，差异显示为"本地已升级，待同步"；
- **升级体验**：库房先出小模型快稿（几秒可用）→ 远程引擎/云在线后自动出精稿 → 指针切到精稿。
  手机/控制台显示"快速稿 · 可升级"或"精稿 · 来自远程引擎"，可对比、可切回；
- **人工修订挂在时间区间上**（§3.4），换稿不丢；对齐重叠度过低时提示确认；
- **手机直连云**：两种凭据模式——手机本地 Key（离线可用，成本/隐私自负）或库房代理
  （Key 只存库房，手机在线时走库房）。产出的 attempt 通过 outbox 回传，带 `audio_sha256`
  让库房校验是同一份录音；离线时先本地生效（标"未同步"），联网后合并，不覆盖别人也不被别人覆盖；
- 旧尝试默认保留（体积小），按"N 天 / 保留前 3 版"清理。

## 13. 多服务端：库房 + 引擎端点（原稿的"工位节点"已简化）

> **修订（2026-10-26）**：原方案把强机做成"工位节点"（注册/心跳/领任务/结果回写），
> 属于过度设计。定稿改为**无状态远程引擎**：强机只跑一个小的 ASR HTTP 服务，
> 库房把它当一个引擎调用；不再有注册、心跳、任务领取、数据复制。
> 本节保留推演过程，最终以 [ARCHITECTURE §1/§6.6](ARCHITECTURE.md) 为准。

### 13.1 一句话

别让两台电脑都当"主服务器"。按角色拆：

| 角色 | 常开？ | 干什么 | 能不能转写 |
| --- | --- | --- | --- |
| **库房（hub）** | 必须常开 | 唯一数据主库：存音频/记录/尝试/人工修订；手机先连它 | **能**，跑小模型出"快稿"（精度低但快） |
| **远程引擎（engine）** | 按需 | 强机上的 OpenAI 兼容 STT 服务，被库房用 HTTP 调用 | **能**，跑大模型出"精稿" |
| **手机** | 一直在 | 录音、阅读、触发转写 | **能**，直连引擎或云 API 出"云端稿"（离线也能用） |
| **中转（relay）** | 可选 | 手机不在家时先收下待转交包裹 | 不能，只做中转 |

一句话记：**数据只有一份主库，算力可以有好几处；转写稿允许多个来源，靠"尝试 + 生效指针"合并（§6.5）。**

### 13.2 手机端：地址簿 + 本地队列

- 服务器配置从"一个地址"改成**地址列表**（名称 + 地址 + 令牌 + 优先级），可增删排序；
- 手机**永远先写本地库 + outbox**，再尝试上传：能连上就传，连不上就排队，录音和阅读不受影响；
- 上传到中转时，返回的是 **"已收下，等库房"**（不是"已同步"），手机显示"待中转"；
- 手机自己用云 API 或远程引擎转出的稿，也是先存本地、再当"尝试"回传库房，不直接改服务器结果；
- 自动选路：同局域网直连 > 中转 > 上次成功的地址；失败自动换下一个，不在设置页手忙脚乱。

### 13.3 三种转写来源怎么分工

- **库房快稿（小模型）**：收到录音就转，几秒钟能看个大概，不占强机；
- **远程引擎精稿（大模型）**：强机服务在线时，库房提交任务取回精稿，替换"生效指针"，旧稿留着可对比；
- **手机直转**：没带服务器、想要最高精度或强机久不在线时用；可直连云 API 或远程引擎；两种 Key 模式——
  手机本机 Key（离线可用）或库房代理（Key 只存库房）；
- 三者都产出**不可变尝试**，谁生效按质量档 + 用户钉住决定（§6.5），**不会互相覆盖**。

### 13.4 远程引擎：强机跑现成的 OpenAI 兼容服务

- 强机直接跑现成的 **OpenAI 兼容语音转文字服务**（LocalAI / Speaches / whisper.cpp 封装等），不用写代码；
- 库房只配一条引擎：`base_url + api_key + model + quality_tier + timeout`；
- **不建库、不跑控制台、不参与同步**；新增/下线引擎 = 加/停一条配置；
- 调用即 `POST /v1/audio/transcriptions`（multipart），要句级时间戳就取 `verbose_json`；
- 长音频按 VAD 切片或厂商异步 API；进度/取消按能力降级（没有就估时 + 断连取消）。

### 13.5 强机不在时

- 库房先出小模型快稿，用户马上能读；精稿任务在库里排队，显示 **"等待更强引擎"**（不是"失败"）；
- 可选升级策略：引擎上线自动升级 / 超过 N 小时自动用云 / 只手动点；
- 不做"自动把任务派到随机一台机器"：单人自托管，可预测比聪明重要。

### 13.6 备份与接管（库房挂了怎么办）

- 库房数据 = SQLite 备份（`sqlite3 .backup`）+ 音频目录 + 尝试/镜像；
  定期同步到第二台（rsync/Syncthing 均可，不用造轮子）；
- 接管是**手动一键**，不是自动选主：
  1. 备用机启动接管，`hub_epoch + 1`；
  2. 手机/引擎拿到新 epoch，之后以新库房为准；
  3. 老库房回来时**降级成普通设备**（先拉一遍变更，再允许写）。
- 为什么不做自动选举：单人场景下"脑裂 + 双写"的代价远大于"手动点一下"。

### 13.7 库房放哪（决定体验上限）

| 方案 | 成本 | 强机不开机时 | 备注 |
| --- | --- | --- | --- |
| NAS / 旧笔记本 / 树莓派 | 一次性几百~千元 | ✅ 同步、阅读、排队都正常 | **推荐**，最符合本项目形态 |
| 云 VPS（只当中转/库房） | 月付 | ✅ 但要考虑隐私与带宽 | 音频上云需加密，只做中转更稳 |
| 手机当主库 | 0 | ⚠️ 单机可用，多设备共享退化 | 不推荐做长期方案 |
| 只用强机 | 0 | ❌ 只能排队，控制台不可用 | 就是现在的痛点 |

所以：**先决定库房放哪，再决定要不要接远程引擎**。没有常开库房，多服务端解决不了根本问题。

### 13.8 协议影响（在 v2 上加，不改主干）

- `records.rev` 之外加 `hub_epoch`；设备/引擎记录自己看到的 epoch，跨 epoch 冲突以新库房为准；
- 库房之间复制直接复用设备协议：**库房也是另一个库房的客户端**（changes/ops/upload 幂等）；
- `audio_sha256` 唯一 + 记录 UUID：重复上传/多路复制都能去重；
- 转写结果走 `transcript_attempts`（只增不改）+ `active_attempt_id`（§6.5），
  多个来源同时产出也不会互相覆盖；
- 新端点：`/cluster/info`、`/cluster/promote`、`/engines`（增删测）、
  `/records/{id}/transcripts`、`/records/{id}/active-transcript`；
- 远程引擎直接用 **OpenAI 兼容 `/v1/audio/transcriptions`**（multipart + `verbose_json`）；
  不自造协议；厂商差异（Deepgram/AssemblyAI/阿里/腾讯等）在库房侧写小适配器。

### 13.9 落地顺序

1. **先做手机多地址 + outbox + 尝试/指针的数据结构**（P1）——不依赖多机，先让"多来源"不打架；
2. 再做**库房小模型快稿 + 远程引擎精稿**（P2）——先出可用稿，再升级；
3. 再做**库房热备 + 手动接管**（P2/P3）——搬家/坏机不慌；
4. 最后做**手机直连云 + 凭据模式**（P3）——离线/最高精度的补充路径。

## 14. 交互逻辑重构（人话版）

### 14.1 为什么乱

不是界面丑，是**同一件事有多个入口、多个状态词、失败没有下一步**。现在的例子：

- 同步：入口在"设置"里，结果只在卡片上一个词；
- 转写：有两条互不相干的路径（一组死配置 + 服务器），点了还可能什么都不发生；
- 详情页四个按钮（转文字 / 重新转写 / 重传 / 下载音频）各管一段，用户得先自己判断该点哪个；
- 同一条记录有四种状态说法（服务器状态、本地推断、同步状态、"云端"标）；
- 控制台 6 个导航页，"转写任务"和"记录库"职责重叠。

### 14.2 三条规矩

1. **一个入口**：同一件事只在一个地方做。
2. **一个状态**：一条记录只有一个流程状态，全端用同一套词。
3. **失败必带下一步**：没有"失败了，然后呢？"。

### 14.3 统一状态词表（手机/控制台/服务端同一套）

`仅本机 · 待上传 · 待中转 · 排队中 · 转写中 36% · 已转写（快稿） · 已转写 · 失败（原因） · 已删除`

"已转写"可以带来源/质量后缀（快稿 · 来自库房 / 精稿 · 来自远程引擎 / 云端稿），
但**只有一个流程状态**；来源只作为附注，不让用户自己拼状态。

技术层可以仍分 record/job/sync 三个维度，但**展示层只翻译成这一个状态**，不再让用户拼。

### 14.4 手机端：把"找入口"变成"看状态"

| 现在 | 改成 |
| --- | --- |
| 设置 → 立即同步 | 列表页顶部**同步条**（待上传 3 · 转写中 1 · 失败 1）→ 点进**同步中心** |
| 详情四个按钮 | 详情一张**任务卡**：状态 + 进度 + 失败原因 + 来源与质量（库房快稿/远程引擎精稿/手机云稿）+ **一个主按钮**（按状态自动变：上传/重试/取消/重新转写） |
| 两组转写设置 | 设置只留"服务器地址簿 + 自动转写开关 + 诊断"；删掉不生效的转写 API |
| 卡片上 3 个标签 | 卡片只留**一个流程标签**，失败可点开原因 |
| 云端/本机两套列表 | 一条列表，流程标签里区分"仅云端"，不再单独一页 |

新用户路径：**扫码 → 连通 → 引擎就绪检查（缺模型就说去哪下）→ 试转一条**，3 分钟闭环。

### 14.5 控制台：把 6 页收敛成 3 个主区

- **记录库**（主）：状态直接长在列表上，筛选/批量/详情；
- **同步与设备**：设备、引擎、库房状态、待处理、失败；
- **系统状态**：引擎是否就绪、模型、队列、最近失败、磁盘；
- 设置/AI 收进角落；取消独立"转写任务"页——任务状态就长在记录上，另给一个**活动中心**看时间线；
- 3 秒轮询改实时推送，列表和详情只更新变化的那部分。

### 14.6 先用小步把"乱"治好（不动数据模型）

1. 统一状态词表 + 首页同步条（约 1 天）；
2. 删死入口、详情四按钮合成一张任务卡（1–2 天）；
3. 控制台导航收敛 + 状态列（2–3 天）；
4. 再谈视觉和布局。

验收标准只有一句：**不看文档的新用户，能自己完成配对、录一条、看到转写结果；任何失败点一下就知道为什么、点哪里修。**
